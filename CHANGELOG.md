## 2026-10-07

- **SD clock raised to 20MHz**, the rider's decision on the numbers below: 0.4 write failures a minute at 20MHz against 1.2 at 10MHz and 3.3 at 4MHz, with flush times no worse.
- **A write failure no longer costs any rows.** Each recovery used to lose 1 to 20 rows silently — sampled while the file was being reopened, discarded before the queue, counted nowhere. Found by comparing rows sampled with rows written; a run with a recovery in it now has every row, each 2ms after the one before.
- **Why SD writes fail, narrowed down.** About 35 minutes of timed bench runs with conditions switched at run time. The failures are bit errors on the link to the card (the card's own checksum rejects them — nothing is ever corrupted silently); their rate follows how long the bus is busy, so a slower clock is worse; the LED, the GPS serial line and the IMU bus were each tested and cleared. The device now keeps its libraries' warnings in memory (`/api/debug/log`), which is what made this visible.
- **500Hz holds with a GPS fix.** RUN0050 (button start) and RUN0051 (dashboard start), bike on the balcony with 11–12 satellites: a fix on every row, every row exactly 2ms after the one before (4642 of 4642, 7650 of 7650), none dropped. The loop was busy for 0.53ms of each 2ms period on average and 1.1ms at worst; reading the GPS took 45µs a pass.
- **The banners for a run that takes the device off WiFi**, confirmed by the rider on the real device. Started from the dashboard: "Recording — WiFi is off during the run. Stop it with the button on the device." Started with the button: "No connection to the device. If a run was started with its button, that is why: WiFi is off while recording." Either way the page came back by itself once the device was on WiFi again.
- **GPS sets the clock.** With the bike on the balcony (fix, 12 satellites, HDOP 0.87) the clock's source went from `ntp` to `gps`, and the device's time matched the PC's to the second.
- **The new start path records cleanly from the button and from the dashboard.** RUN0048 (18.1s) and RUN0049 (13.8s), the rider's own start/stop tests on the bench: every row exactly 2ms after the one before (9051 of 9051, 6911 of 6911), 500 rows from the very first second, none dropped.
- **No more hole at the start of a run.** The WiFi radio is taken down before the run's file is opened, instead of half a second into the recording, where it left 75–115ms without rows. A 12s bench run now has exactly 6000 rows, 500 in every second including the first. A start from the dashboard is answered first and carried out half a second later.
- **"1000 Hz (Beta)" in Settings**, with a "Rows dropped" badge in the Runs list for any run where the SD card could not keep up — until now that count was only in the run's `.JSON`.
- **The sampling loop delivers the configured 500Hz.** 283–288 rows a second before (it varied with every firmware build: 398, 387, 375…), 500 in every full second after, rows exactly 2ms apart, none dropped in a 60s bench run. The ADC reads were 79% of every pass; they, the LED, the GPS read and the row's GPS maths were made cheap, and the samples got a clock of their own. Measured on the device with a loop profiler and timed runs that stop by themselves (`/api/debug/loop`, `/api/run/timed`).
- **Checked on real screens by the rider.** Every page opens in the tablet's and the phone's own browsers (with the files now served gzipped). The "Recording — WiFi is off" banner appears when a run starts and the page comes back on its own when it ends. A Settings edit survives a reload. Chart zoom and the segment/event rows work by touch on the tablet. The light theme. The run charts fit the window, the pinned time axis reads well while scrolling and 52px per row is still readable. The zoomed stretch is easy to find on the map.
- **A new run gets `start_utc`.** RUN0047: 11:42:56 local, shown in the runs list and on the run page.
- **The active bike's profile keeps itself up to date.** Every setup edit is written into the saved profile, renaming the bike renames it, and Save As… switches to the new profile. Came out of checking the Tyee 5 profile, which could not be read back at all; it can now (`/api/bikes/profile?name=`), and it matched the live settings in all 26 fields (rear Volume Tokens 1, rear pressure 235 psi).
- **Refraction off the cards.** No scroll problem on the tablet or the PC, but no visible effect there either; it stays on the top bar, the navigation and the tab bars, where it shows.
- **Gzip the web files.** 415KB → 120KB in the filesystem image; the run page's download went from 263KB to 78KB. Needed more than the build step: the firmware's routes had to change too (`serveWebFile()` — see [troubleshooting.md](docs/troubleshooting.md)).
- **Map follows the zoom.** The route fades and the zoomed stretch is drawn over it, on the Leaflet map and on the SVG fallback.
- Run page: one pinned time axis for the seven charts, rows fitted to the window's height, zoom by segment/event with Avg/Peak following the zoom.
