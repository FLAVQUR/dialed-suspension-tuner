# Dialed — Task list

This is the working list. [summary.md](summary.md) is the record: what exists, why, and what was learned on the way.

How it is used:
- When an item is done, it gets the date and moves to **Done**, at the end.
- In the same step, whatever is worth keeping goes into `summary.md` (what was built, why it was built that way, what went wrong).
- New ideas go into the section they belong to; anything turned down goes to **Parked by decision**, so it isn't proposed again.

## Now — without the bike

- [ ] **The device resets when the card holds too many runs** (2026-10-11, with 104 test runs on it: starting a run and listing the runs both ran past the 8s watchdog; see "SD card write path" in `summary.md`). Measure where it starts — time `nextRunNumber()` and `/api/runs` at 20, 40, 60, 80 runs — then stop both from growing with the card: keep the next run number instead of scanning for it, and send the list in pieces. Until then, keep the card well under 100 runs.
- [ ] **Show what a run is missing.** The run's `.JSON` now says it (`rows_lost`, `rows_dropped`); the run page and the list still only say "incomplete" or "rows dropped". Half a second missing from 97 is not the same as a run cut short.
- [ ] *(Small)* **The line each recovery leaves short of its last two columns.** Its data is intact; either finish the line on replay or have the parsers accept it. Matters less now that recoveries should be rare.
- [ ] *(Idea)* **Correct a run's recorded setup from its page.** The endpoint takes clicks, tokens and pressure (`POST /api/runs/setup`), but only the lockout has a control. Worth one if a run is again recorded with Settings that were not what was on the bike.
- [ ] *(Idea)* **Sleep instead of spinning between samples.** The loop now idles for 79% of every sample period, in a busy wait. Sleeping through most of it would cut the current draw on a ride. Not done with the rewrite, to keep the timing change small.

## With the bike or on a real screen

- [ ] **Rear shock: add a volume token** (1 → 2; the stock can takes 4). *Waiting on the part: the rider has no spare token and expects to 3D-print one.* +10 psi was ridden on 2026-10-10 and was not enough: 2 bottom-outs against 3 on the warm-up track, 3 and 3 against 3 and 4 on the aggressive one, at the same points. Enter the token in Settings and recapture the static sag before riding; then compare against RUN0047–49 the same way. After tokens, the Linear XL can.
- [ ] **The SD fix on a ride** (driver status check, buffers — 2026-10-11, bench only). What to read in each run's `.JSON`: `sd_recovered` should be 0 or close to it where it was 0–11, `incomplete` false, `rows_dropped` and `rows_lost` 0; if a recovery does happen, `sd_recover_max_ms` and the three `sd_*_failed` counts say how it went. Afterwards `GET /api/debug/log` shows how many stray statuses the driver absorbed — only for the last few runs, and only if the device has not been restarted.
- [ ] **Harsh events.** Check them against a run remembered as harsh. Only then decide whether they are reliable enough to feed the Tuning tab.

## Secondary

- [ ] **"Possible need for service" signal**: logarithmic decrement/ζ per impact, sag drift between sessions. The setup history it was waiting for exists now — compare runs inside one stretch of `setupEpochs()`, where a drift is not explained by a setup change.
- [ ] *(Low)* **SD card: the bit errors that are left on the link.** What made runs fail turned out to be the driver, not the wires (2026-10-11). What remains is a command the card rejects for its checksum about once a minute (`sdCommand(): crc error` in `/api/debug/log`), which the driver repeats by itself and costs nothing. Only worth the hardware work — a decoupling capacitor at the card socket, the ground return, wire lengths, a scope on the clock line — if that rate climbs.

## Future nice-to-haves

- [ ] *(Idea, 2026-10-08)* **An AI second opinion in the Tuning tab.** On request, send a model what the page has already worked out for the run — the evidence behind the suggestions, the events, the segments, the setup and its history, the rider's notes, the bike's components — and show its reading under the rule-based suggestions, which stay. Not the telemetry itself (megabytes). Open points: the call has to come from the browser (the device has neither the memory nor the flash to spare for TLS) and only works where the browser has internet, so not on the device's own access point; where the API key lives, given the pages are served over plain HTTP; and keeping the answer in the run's `.JSON` so it is still there offline. A first step that needs none of that: a "Copy for AI" button that puts the same summary on the clipboard.
- [ ] **Multilingual UI.** The dashboard is English only. The idea is a UI that can be shown in more than one language, rather than a translation of the strings in place.

## Parked by decision — don't pick up unless asked

- **Sampling at 1000Hz.** 500Hz was taken off this list and done on 2026-10-07; 1000Hz stays here for now. The loop has the headroom for it on paper (it is busy for about a quarter of a 500Hz period), but it doubles what the SD write path has to take, and that path lost rows on its first ride at 500Hz (2026-10-10; fixed on the bench the next day, not ridden since). The option stays selectable in Settings, labelled "1000 Hz (Beta)"; what is parked is the work of testing it and making it dependable.
- **IMU at 3MHz.** Already confirmed to break again; it stays at 400kHz.
- **Checking for internet on the ESP32 itself.**
- **A warning when firmware and dashboard don't match.** Turned down on 2026-10-08: the two are always uploaded together instead (`pio run -t upload` does both).

- 2026-10-11 — **Guided calibration works with real captures** (confirmed by the rider): Zero → Max → Sag, used to recalibrate the front and recapture the static sag before the ride of 2026-10-10.
- 2026-10-11 — **The SD "sync failures" explained and fixed, on the bench.** They were never failed writes: the framework's SD driver takes a stray `0x03` in the card's status after a write for an error. A project copy of the driver (`lib/SD`) asks again before failing. Alongside: rows wait in the queue when the replay buffer is full instead of being thrown away, the two buffers were rebalanced (queue 448, `pending` 192), `pending` is flushed before it can overflow, and the run's `.JSON` says how recoveries went and how many rows a run is missing. See "SD card write path" in `summary.md`.
- 2026-10-10 — **Field test: 500Hz, the setup history and +10 psi, on a ride.** RUN0047–50. 500 rows/s with none dropped at the queue; the setup history shows the change to 235 psi where it should; both static sags were recaptured first. - 2026-10-07 — **SD clock raised to 20MHz**, the rider's decision on the numbers below: 0.4 write failures a minute at 20MHz against 1.2 at 10MHz and 3.3 at 4MHz, with flush times no worse.
- 2026-10-07 — **A write failure no longer costs any rows.** Each recovery used to lose 1 to 20 rows silently — sampled while the file was being reopened, discarded before the queue, counted nowhere. Found by comparing rows sampled with rows written; a run with a recovery in it now has every row, each 2ms after the one before.
- 2026-10-07 — **Why SD writes fail, narrowed down.** About 35 minutes of timed bench runs with conditions switched at run time. The failures are bit errors on the link to the card (the card's own checksum rejects them — nothing is ever corrupted silently); their rate follows how long the bus is busy, so a slower clock is worse; the LED, the GPS serial line and the IMU bus were each tested and cleared. The device now keeps its libraries' warnings in memory (`/api/debug/log`), which is what made this visible.
- 2026-10-07 — **500Hz holds with a GPS fix.** RUN0050 (button start) and RUN0051 (dashboard start), bike on the balcony with 11–12 satellites: a fix on every row, every row exactly 2ms after the one before (4642 of 4642, 7650 of 7650), none dropped. The loop was busy for 0.53ms of each 2ms period on average and 1.1ms at worst; reading the GPS took 45µs a pass.
